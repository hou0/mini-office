# ADR 0005：插件扩展系统与主题插件

- 状态：提议中
- 日期：2026-10-29
- 决策者：Mini Office 工程组
- 关联：`docs/plugin-architecture.md`

## 背景

客户反馈："主体保持 mini，可以参考 deepseek harness 的插件概念扩展能力，毕竟不同的使用者需求不一样。"

产品方向明确：内核保持轻量，重点投入文档编辑、排版、打印；个性化与行业能力通过插件扩展。
同时需要支持主题插件（Office 风格、WPS 风格、经典 XP / Office 2003 风格）。

现有代码已具备两项关键条件：

1. UI 全部由 `--mo-*` CSS 自定义属性驱动，主题切换唯一入口为 `applyTheme` / `applyAccent` / `applyAppearance`，
   切换主题不需要重渲染组件。
2. 已存在注册表模式先例：`registerFormatHandler` + 懒加载（`packages/document-model/src/store.ts`）。

候选方案：

1. **全能力 Extension Host**（VS Code 式）：插件可任意操作 DOM、访问 Node API。
2. **声明式插件优先 + 窄 API 沙箱**：分级信任，绝大多数定制不执行代码。
3. **不做插件系统**，按客户需求定制分支。

## 决策

采用**方案 2**：三级信任模型的插件系统。

- **T1 声明式**：纯数据（manifest + tokens + 受限 CSS），不执行代码。承载主题、模板、快捷键、工具栏布局。
- **T2 沙箱**：JS 跑在 Worker，UI 跑在 iframe，仅通过 RPC 访问文档模型。承载导出、校对、批处理。
- **T3 受信**：JS + Rust 原生能力，需签名与显式授权。承载 OCR、AI、企业对接。

配套决策：

- 插件只能依赖 `@mini-office/plugin-api`，不得引用任何内部包。
- 主题包分两层：**Token 层**（颜色/圆角/字体/密度）与 **Chrome 层**（外壳渲染变体枚举）。
  仅换颜色无法实现 Office 2003 风格，必须有结构层。
- `--mo-doc-*`（文档画布字体度量）与 UI 令牌**强制分离**，主题无权修改文档渲染，
  以保证同一文件在任意主题下页数与打印结果一致。
- 内核边界判据：**出错是否会导致文件损坏/内容丢失/安全失守**。会 → 内核；不会 → 插件。
- 内置功能（邮件合并、主题色、导出目标）优先以插件 API 实现，确保 API 被真实使用。

### 功能插件：v1 只做宏，不做脚本

客户要的"定制功能"多数是一串固定的文档操作。因此 v1 的 `commands` 贡献点只接受
**宏**——JSON 描述的操作序列，由宿主按白名单解释执行，插件不跑代码。

这样功能插件仍属 T1：安装不需要签名、不需要审核、不需要权限声明，
同时又能覆盖"套用公文版式""表格转三线表""表头加底纹"这类真实需求。

需要控制流或真正执行逻辑的功能（校对、OCR、格式转换、AI）不扩宏语言，直接归 T2。
**不把宏做成脚本语言**，是刻意的克制：一旦需要 if/for，说明该上沙箱了。
详见 `docs/plugin-macros.md`。

### 分发：GitHub 仓库替代插件商店

**不建商店。** 官方插件放在公开 GitHub 仓库，客户端通过 GitHub API 拉取 `index.json`，
`.moext` 包提交进 `packages/` 经 `raw.githubusercontent.com` 分发，索引中固化 SHA-256 供安装时校验。

> 原始方案是挂 Release 资产，实测不可行：Release 下载会 302 到 `objects.githubusercontent.com`，
> 该域不返回 CORS 头，WebView 里的 `fetch` 被拦截。详见 `docs/plugin-architecture.md` §10.5。

同时下调 T3 的定义：

| 机制 | 原计划 | 调整后 |
|---|---|---|
| 商店 | P3 建审核与分发平台 | **取消**，由 GitHub 仓库 + `index.json` 替代 |
| 签名 | 商店插件强制 Ed25519 | **仅企业侧载需要**，个人场景由 SHA-256 完整性校验覆盖 |
| 审计 | P3 建审计表 | 提前到 P2，先做本地权限与写入记录 |

理由：客户要的是"能装插件"，不是"有一个插件市场"。商店需要服务器、审核人力与运营，
而 GitHub 方案把这三项成本降为零；SHA-256 已能覆盖防篡改与防下载不完整，
签名真正不可替代的场景只有企业受管环境下的发布者身份验证。


## 理由

- **体积**：方案 1 需引入完整 Node 运行时，安装包增加数十至上百 MB，直接违背"轻量、快速"前提。
- **安全**：办公套件处理用户真实文件，插件任意读写 DOM 会绕过 L0–L3 能力分级与未知部件保留策略。
- **覆盖面**：客户最常提的定制（主题、模板、快捷键、菜单精简）本质是数据，T1 即可满足，
  且可全自动加载、无需审核、失败影响面为零。
- **可演进**：T2/T3 的 API 可在 T1 上线后依据真实插件需求收敛，避免过早固化接口。
- **可验证**：`registerFormatHandler` 已证明注册表模式在本项目可行，风险可控。

## 后果

正面：

- 内核不再为个别客户需求膨胀，新增能力默认走插件。
- 主题可零成本分发，客户可自建（政府红头、高对比无障碍、护眼暗色等）。
- 插件故障与内核隔离，不影响文档保存。

负面 / 代价：

- `AppShell` 需重构为"插槽 + 渲染变体"骨架，这是 P1 的主要工作量，且会触及现有外壳代码。
- 插件表达力受限：不能任意改 UI、不能直接操作 DOM、不能随意访问文件系统。
- 需要维护 `plugin-api` 的 semver 兼容承诺与弃用流程。
- 引入新的攻击面（插件供应链），需要签名与审计，P3 前存在缺口。

## 被否决的方案

- **方案 1（全能力 Extension Host）**：体积与安全代价不可接受。
- **方案 3（定制分支）**：维护成本随客户数线性增长，且分支间无法共享修复。

## 待补充

- `chrome.toolbar: 'classic-two-row'` 需要把 `AppShell` 抽成插槽 + 渲染变体，
  这是"Office 2003 风格"能否立住的关键，工作量需单独评估。
- 主题是否应带走强调色（当前 `applyAccent` 的内联样式优先级更高，`defaultAccent` 不生效）。
- 插件文件存储是否从 IndexedDB 切换到原生目录（换取热重载，代价是新增 Rust 命令）。
- **宏是否要支持按选区执行**：选区状态在各编辑器内部，需要 T2 的命令总线统一暴露。
  在此之前宏只能作用于整篇文档。
- **MCP 支持**：已定调为 T3 插件而非核心功能，依赖 T2 的命令总线，
  详见 `docs/plugin-architecture.md` §15。
