# ADR 0001：编辑引擎选型

- 状态：已采纳
- 日期：2026-10-18
- 决策者：Mini Office 工程组

## 背景

PRD 要求离线优先、轻量、三格式兼容，并明确“UI 精简不等于破坏原始文件”。
候选方案包括：

1. 嵌入 ONLYOFFICE Desktop Editors / Univer 等成熟编辑器内核。
2. 以 LibreOffice Headless 作为后端转换/渲染。
3. 自建 TypeScript OOXML 模型 + 浏览器排版/网格/幻灯片渲染。

## 决策

采用 **Tauri 2 + React + TypeScript + 自建 OOXML 适配层**：

- DOCX：自建解析 + 分页测量 + 段落级 `contentEditable` 编辑 + 主文档重写。
- XLSX：自建解析 + 虚拟网格 + 自研公式引擎 + 工作簿重写。
- PPTX：自建解析 + 高保真渲染 + 原始 OOXML 增量回写；基础内容编辑优先，复杂效果保留原部件。
- Rust/Tauri 负责文件、安全扫描、原子存储、字体、平台能力；不把排版引擎放进 Rust 首版。
- LibreOffice Headless 仅保留为 `office-pdf` 中的 PoC 对照后端，不作为运行依赖。

## 理由

- **文件安全可控**：可以精确决定“写回哪些部件、保留哪些未知部件、何时只读/另存”。
  成熟 Web 编辑器往往以自身模型为主，导入/导出会重建包，未知对象容易丢失。
- **包体与启动**：不引入数百 MB 的 Chromium/ONLYOFFICE 运行时或 LibreOffice 安装。
- **许可确定性**：不直接分发 AGPL/商业双许可内核，避免在闭源桌面产品中的合规不确定性。
- **中文排版可调**：字体替代、首行缩进、固定行距、分页与打印可以按中文合同需求调整。
- **可测试**：OOXML 解析、序列化、公式引擎均可在 Node/Vitest 中直接回归。

## 后果

### 正面

- 完全掌控保存与兼容策略，能把 L0–L3 分级、只读、另存副本、原子保存落到代码。
- 无重量级引擎依赖；Web 包约 665 KB（gzip 约 211 KB）+ 按需 PDF chunk。
- 桌面/Web/未来移动端共享同一套文档模型与编辑器 UI。

### 负面 / 风险

- 需要持续投入 OOXML 兼容覆盖：样式继承、复杂表格、图表、批注、修订、域等。
- 高保真 PPT 渲染与复杂 DOCX 分页无法在 V1 达到 Office 原生水平。
- PDF 目前是 DOM 截图，不是矢量排版；大文档的内存/清晰度需要优化。
- 自研编辑器的撤销、协作、输入法等边界需要长期打磨。

## 备选方案评估

| 方案 | 优点 | 不采用原因 |
|---|---|---|
| ONLYOFFICE 嵌入 | 高兼容、编辑功能完整 | 体积/启动、AGPL/商业许可、文件模型与安全保存不可控、定制成本 |
| Univer | 表格体验好、可嵌入 | 主要覆盖表格；Word/PPT 覆盖不足；许可与商业模块需审核 |
| LibreOffice Headless | 转换成熟、格式多 | 包体大、冷启动慢、交互编辑不可行、版权/打包复杂；仅适合 PoC 对照 |
| 浏览器直接 contentEditable 作为文件模型 | 开发快 | 违反 PRD：不能把 DOM 当真实 Office 模型，保存会破坏文件 |

## 复核条件

出现以下情况应重新评估：

- 目标合同/工作簿/演示的真实兼容通过率长期低于可接受阈值；
- 自研维护成本超过产品收益；
- 有许可清晰、包体可接受、支持“保留未知部件”的成熟内核。
